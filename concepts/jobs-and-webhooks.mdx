Most calls answer in the same request. Crawls and batches cover many pages, so they run as background jobs: you get an id back, then poll it or let a webhook tell you when it is done.

| Call | What you get back |
| --- | --- |
| Scrape | `{ data }` once the page is read. Set `async: true` to get `{ jobId, status }` straight away instead. |
| Map, Search, News, Extract, Brand, Screenshot, Images | `{ data }` once the work is done |
| Crawl | Always `{ crawlId, status }`. Poll it or use a webhook. |
| Batch | Always `{ batchId, status }`. Poll it or use a webhook. |

## Scrape

A scrape waits for the page and returns it:

```json
{
  "data": {
    "url": "https://example.com",
    "status": 200,
    "markdown": "# Example Domain\n\n..."
  }
}
```

A scrape that waits gets up to **90 seconds**. If the page takes longer, the call fails with `504` and `REQUEST_TIMEOUT`, and costs nothing. It never turns into a job by itself, so you only ever handle one response shape.

For pages you expect to be slow, such as heavy JavaScript apps, set `async: true`. The call answers at once with `201`:

```json
{
  "jobId": "019f3c09-6fae-740f-9257-10c2b6af7f43",
  "status": "queued"
}
```

Then poll it:

<CodeGroup>

```bash cURL
curl https://api.hydrafetch.com/v1/web/scrape/019f3c09-6fae-740f-9257-10c2b6af7f43 \
  -H "X-API-Key: hf_your_key_here"
```

```javascript Node
const res = await fetch(
  "https://api.hydrafetch.com/v1/web/scrape/019f3c09-6fae-740f-9257-10c2b6af7f43",
  { headers: { "X-API-Key": "hf_your_key_here" } },
);
const job = await res.json();
```

</CodeGroup>

<ResponseField name="status" type="string">
  `waiting`, `active`, `completed` or `failed`.
</ResponseField>
<ResponseField name="data" type="object">
  The page, once `status` is `completed`.
</ResponseField>
<ResponseField name="error" type="string">
  Why it failed, when `status` is `failed`.
</ResponseField>

## Crawl and batch

A crawl finds and reads the pages of a site. A batch reads a list of URLs you give it. Both always run in the background. Starting one answers at once with `201`:

<CodeGroup>

```json Crawl
{
  "crawlId": "019f3c09-6fae-740f-9257-10c2b6af7f43",
  "status": "queued"
}
```

```json Batch
{
  "batchId": "019f3c09-6fae-740f-9257-10c2b6af7f43",
  "status": "queued"
}
```

</CodeGroup>

Then follow it in either of two ways. You can also use both.

<Tabs>
  <Tab title="Poll">
    Ask for the job's status to see progress and each finished page:

    ```bash
    curl https://api.hydrafetch.com/v1/web/crawl/019f3c09-6fae-740f-9257-10c2b6af7f43 \
      -H "X-API-Key: hf_your_key_here"
    ```

    Batches use `GET /v1/web/batch/{id}`. Both answer in the same shape:

    ```json
    {
      "data": {
        "id": "019f3c09-6fae-740f-9257-10c2b6af7f43",
        "kind": "crawl",
        "status": "running",
        "total": 100,
        "completed": 42,
        "failed": 1,
        "creditsUsed": 42,
        "pages": [
          { "url": "https://example.com/blog/post", "status": "completed", "depth": 1, "data": { } }
        ]
      }
    }
    ```

    `status` goes from `running` to `completed`, or ends as `failed` or `cancelled`. Each entry in `pages` has its own `status` and, once read, its `data`. Results stay available for 90 days after the job last changes. After that the status call answers `404`.
  </Tab>
  <Tab title="Webhook">
    Add a `webhook` when you start the job, and we call your URL as pages finish and again when the job ends. You do not need to poll.

    ```bash
    curl -X POST https://api.hydrafetch.com/v1/web/crawl \
      -H "X-API-Key: hf_your_key_here" \
      -H "Content-Type: application/json" \
      -d '{
        "url": "https://example.com",
        "limit": 100,
        "webhook": {
          "url": "https://your-app.com/hooks/hydrafetch",
          "events": ["page", "completed"],
          "secret": "whsec_a_long_random_string",
          "headers": { "Authorization": "Bearer your-token" }
        }
      }'
    ```

    | Event | When it is sent |
    | --- | --- |
    | `crawl.page` or `batch.page` | Each time a page finishes, with that page's `status` and `data` |
    | `crawl.completed` or `batch.completed` | Once, when the job ends, with the full job status |

    <ParamField body="webhook.url" type="string" required>
      Where we send events. It must be a **public** http or https address. Private, loopback and link-local addresses are refused with `400`.
    </ParamField>
    <ParamField body="webhook.events" type="string[]">
      Which events you want: `page`, `completed` or both. Both by default. Use `["completed"]` to get only the final result.
    </ParamField>
    <ParamField body="webhook.headers" type="object">
      Extra headers sent with each call, for example to authenticate us to your endpoint.
    </ParamField>
    <ParamField body="webhook.secret" type="string">
      A shared secret. When set, every call is signed so you can check it came from us. See [Verifying a webhook](#verifying-a-webhook).
    </ParamField>

    <Note>
      If your endpoint is down or answers with anything other than 2xx, we retry with growing gaps, up to 6 attempts.
    </Note>
  </Tab>
</Tabs>

## Verifying a webhook

Your webhook URL is public, so anyone who finds it can send to it. Set `webhook.secret` and we sign every call, so you can reject anything that did not come from us.

Each signed call carries these headers:

| Header | What it holds |
| --- | --- |
| `X-Hydrafetch-Signature` | `t=<timestamp>,v1=<hmac>`: an HMAC-SHA256 of `<timestamp>.<raw body>`, keyed with your secret |
| `X-Hydrafetch-Timestamp` | Unix seconds when we sent it |
| `X-Hydrafetch-Event` | The event, such as `crawl.completed` |
| `X-Hydrafetch-Delivery` | A unique id for this attempt |

To check a call, compute the HMAC over the **raw request body** exactly as received. Parsing the JSON and turning it back into text can change the bytes, and then it will never match.

```python
import hashlib, hmac, time

def verify(raw_body: bytes, signature_header: str, secret: str, tolerance_s: int = 300) -> bool:
    parts = dict(p.split("=", 1) for p in signature_header.split(","))
    timestamp, received = parts["t"], parts["v1"]

    if abs(time.time() - int(timestamp)) > tolerance_s:
        return False

    expected = hmac.new(
        secret.encode(), f"{timestamp}.".encode() + raw_body, hashlib.sha256
    ).hexdigest()
    return hmac.compare_digest(expected, received)
```

<Warning>
  Compare signatures with a constant-time function such as `hmac.compare_digest` or `crypto.timingSafeEqual`. A plain `==` can leak the secret through timing. Always check the timestamp too: without it, someone who captures a real call can send it to you again later.
</Warning>

The timestamp is signed together with the body, so nobody can resend a real call under a new timestamp. If you set no secret, calls are still sent, just unsigned.

## Did my webhook arrive?

We keep the history of every call we tried for a job: its status, how many attempts we made and what your endpoint answered last.

```bash
curl https://api.hydrafetch.com/v1/web/crawl/019f3c09-6fae-740f-9257-10c2b6af7f43/deliveries \
  -H "X-API-Key: $HYDRAFETCH_API_KEY"
```

Batches use `GET /v1/web/batch/{id}/deliveries`.

<ResponseField name="deliveries" type="object[]">
  <Expandable title="WebhookDelivery">
    <ResponseField name="id" type="string">The delivery's id.</ResponseField>
    <ResponseField name="event" type="string">The event it carried.</ResponseField>
    <ResponseField name="status" type="string">`pending` while retries remain, `success` once delivered, `failed` once we gave up.</ResponseField>
    <ResponseField name="attempts" type="number">How many attempts we have made.</ResponseField>
    <ResponseField name="responseStatus" type="number | null">The HTTP status your endpoint returned last time.</ResponseField>
    <ResponseField name="error" type="string | null">Why the last attempt failed, if it did.</ResponseField>
    <ResponseField name="deliveredAt" type="string | null">When it was delivered, in ISO 8601.</ResponseField>
    <ResponseField name="createdAt" type="string">When it was first created, in ISO 8601.</ResponseField>
  </Expandable>
</ResponseField>

A `failed` delivery with a 5xx `responseStatus` usually means your endpoint was down. A 4xx means we reached you and your endpoint refused the call, so check your signature code before assuming the payload is wrong.
